03 · Decision logic

One threshold, two outcomes

For every frame and every channel, the pipeline reduces the image to a single scalar — the mean pixel value inside the active mask — and compares it to the setpoint.

decision 2 mean ≥ setpoint → add acidic media
decision 1 mean < setpoint → add neutral media
decision 3 (not emitted by current logic) → add basic media
Setpoint initialization. On startup, CreateDecisions computes each channel's setpoint as 2 × mean_luminosity(frame_0, ch) and writes it to setpoint_file. The file is re-read every frame, so edits made through the GUI's setpoint manager take effect on the very next decision — no restart needed.
04 · Pulse state machine

Four experiments, two independent 30 s timers

SendDecisions keeps one timer per channel. Their combined state selects which .OnixExp template runs. Expiry is purely time-driven — it does not need a new decision to fire.

On any state change SendDecisions aborts the current ONIX experiment thread (via abort_event, 15 s join timeout) and starts the new one in a fresh daemon thread. Each experiment is a Windows .OnixExp template: NN.OnixExp, AN.OnixExp, NA.OnixExp, AA.OnixExp. The hardware's RunState is polled back to idle before the next template is opened.

06 · Filesystem layout

Seven directories, seven contracts

Every directory has exactly one writer. That is how the system stays correct without locks.

global_path/ 
├── watch_dir/ raw microscopy PNGs land here writer: microscope
├── mask_dir/ Cellpose masks + ROI metadata archive writer: HandleSegmentations
├── curr_mask_dir/ frame-0 reference masks used for every decision writer: user (GUI / preprocess.ipynb)
├── decision_dir/ per-channel intermediate decision files (ephemeral) writer: CreateDecisions
├── final_dir/ actions.toml + media_status.json writer: CreateDecisions · SendDecisions

07 · Startup sequence

How the loop closes

There is a deliberate gate at the beginning of every experiment: nothing runs until the operator has approved frame-0 segmentation.

1

Operator tunes & pushes frame-0 masks

Inside the GUI's Segmentation tab (or preprocess.ipynb), the user adjusts Cellpose parameters (diameter, flow threshold, cellprob, niter) until the mask looks right, then clicks Push mask. This writes 00000_channel{c}.npy into curr_mask_dir/.

2

Operator starts the pipeline from the GUI

Clicking Start on the Pipeline tab invokes POST /api/pipeline/start, which runs bash run_system.sh. The script calls config.py synchronously to ensure every directory exists and config.json is fresh.

3

Four monitors launch in parallel

CreateDecisions.py unblocks the moment it sees curr_mask_dir/00000_channel{c}.npy for every channel and uses those masks for the entire run. SendDecisions.py establishes the ONIX session and starts the neutral NN.OnixExp. MonitorPerformance.py begins polling mask_dir. If continuous_segmentation=true, HandleSegmentations.py joins them; otherwise the user-pushed masks are the only ones used.

4

The closed loop runs

Every new frame → segmentation (optional) → luminosity check → actions.toml → pulse timer → ONIX state change. The GUI polls /api/log/tail, /api/media-status, and /api/frames every second so the dashboard stays live.

08 · Subtle but critical

Mask ownership rule

!

curr_mask_dir is user territory · mask_dir is automation territory

mask_dir/ is the automation archive — HandleSegmentations writes every Cellpose result here, and MonitorPerformance reads metadata from it. curr_mask_dir/ is only written by the operator (GUI "Push mask" button or preprocess.ipynb). CreateDecisions exclusively reads its initial per-channel masks from curr_mask_dir/ and reuses them for every frame — so your tuned segmentation is the canonical ROI for the entire run. Mixing these two directories is the fastest way to break the feedback loop.

09 · Failure modes

How the system recovers

None of these require operator intervention — the pipeline is designed to stall safely or self-heal.

ONIX server unreachable

On startup, the connectivity check logs a WARNING; any failed experiment thread causes the main watcher to back off for 5 s before re-spawning. No hot-loop server spam.

Frame-0 masks never pushed

CreateDecisions blocks at wait_for_file(curr_mask_dir/00000_channel{c}.npy) and logs a reminder every 60 s. Nothing downstream fires until the operator approves masks.

Wedged ONIX experiment (RunState=1 on startup)

Each new experiment begins with Abort() + a poll for RunState ∈ [0, -2, 30] before creating the next template. Dangling hardware state can't cascade into the next run.

Partial writes to actions.toml

CreateDecisions writes to {frame}.lock first and uses os.rename to publish. SendDecisions always sees a complete file, then deletes it to prevent re-application.

Stuck microscope / corrupted frame

HandleSegmentations retries image reads up to num_tries=30 with sleep_time=0.2 s (≈ 6 s), logs an error, and moves on. One bad frame never halts the pipeline.

Disk filling up

MonitorPerformance runs a cleanup every cleanup_interval_sec (30 min): files older than retention_time_hours (3 h) in mask_dir and temp_overlays are compressed into archive_YYYYMMDD.zip.
