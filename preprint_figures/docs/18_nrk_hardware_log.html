Diagnostic / QC · 18 · nrk_hardware_log.py

NRK hardware log

Telemetry from the PE_Pipeline V5 feedback controller: the actual luminosity it was reading, the setpoint it was trying to hit, and every "add acidic media" decision it made. NRK only — silently skipped for C2C12 / PC3.

How to read this figure

  1. Black line = real-time luminosity the controller saw.
  2. Filled bands = setpoint regions; horizontal line at the top = target.
  3. Vertical orange spans = acid pulses (after dedup).
  4. Dotted vertical line = real setpoint event.
Purpose

Did the feedback loop behave?

NRK acid experiments are closed-loop: hardware reads luminosity, fires acid when it drops below a setpoint. This figure exposes what the controller actually did — was it tracking setpoint? Did it pulse appropriately? When did it switch to its second setpoint (the "real setpoint" event)? Used to validate the experiment itself, distinct from validating the cellular response.

If the experiment name doesn't match nrk_acid_13APR26, the script returns immediately. No figure for non-NRK experiments.

Inputs

What it reads

  • Direct file read. Loads luminosity_log_channel{N}.json from the same directory as the stim config. Each entry: {"frame": int, "mean_luminosity": float, "channel": int, "decision": str, ...}.
  • state["real_setpoint_min"][exp][ch] — minutes-since-start of the second setpoint event (the transition from initial stabilization to the experiment's "real" target).
  • Config: stim_duration_minutes (default 0.5 min), time_window_minutes (default 30 min for plot range).
Method

Parse, dedup, plot

  1. Load the JSON log for each channel; filter to entries matching the channel number; sort by frame.
  2. Identify setpoint regions. Call setpoint_regions_from_log() to find contiguous frame ranges where the controller held the same setpoint target. Returns a list of (start_frame, end_frame, setpoint_value).
  3. Identify acidic pulses. Filter entries where decision == "add acidic media". Then dedup with _dedup_close_frames(...) using PULSE_DEDUP_FRAMES = 10: pulses within 10 frames of the previous pulse are merged into one.
  4. Convert frames to minutes via frames_to_min.
  5. Plot. Single-panel figure (12 × 6 in, 100 dpi). Layered:
    • Black line: mean luminosity vs minutes.
    • Filled rectangles per setpoint region (skip the initial calibration region) — colored from a fixed palette, alpha 0.3, capped at the setpoint value. Horizontal line at the setpoint height.
    • Legend deduped: only first occurrence of each unique setpoint value gets labeled.
    • Vertical orange/yellow bars (axvspan) at each acid pulse, alpha 0.30, width = stim duration (default 30 s).
    • Vertical dotted black line at the real setpoint event time, zorder=5 to keep on top.
  6. Set y-axis range to [min − 2, max × 1.05] based on luminosity values within the time window. Set x-axis to [0, time_window_minutes].
  7. Print summary to console: frame count, pulse count, setpoint region count, real setpoint time.

What the cell biology says

Expected trends · interpretation

Well-behaved control loop

The black luminosity line tracks the horizontal setpoint with small over/undershoots. Acid pulses are infrequent and effective — luminosity rebounds back to setpoint after each pulse. System is in steady state.

Initial stabilization

Early in the experiment, the controller is finding its setpoint. Expect dense pulses, larger excursions. The first setpoint region is the calibration period (intentionally not labeled in the legend).

Setpoint switch

Around the dotted "real setpoint" line, the target value changes (the colored band shifts). Cell response post-switch is the experimental phenotype of interest. Pre-switch is the baseline.

Excessive pulsing

Many vertical orange bars in a short window means the controller is struggling — luminosity keeps dropping below setpoint after each pulse. Could indicate cell unresponsiveness, very fast acid washout, or controller tuning issues.

Setpoint not reached

Black line consistently below the setpoint horizontal. The system never stabilizes. Either too few pulses (rare), or pulses don't sustain the response. Compare to the per-cell traces in time_traces.

Y-axis suspicions

If luminosity tops out at a flat ceiling, the camera is saturating. The controller can't measure further increases. Reading "perfect setpoint tracking" from such data is misleading.

Watch out

Pitfalls

What the figure can hide

Pulse dedup window. PULSE_DEDUP_FRAMES = 10 is matched to ~1 Hz acquisition. If the frame rate changes, distinct pulses get merged into one (too coarse) or single decisions appear as many (too fine).

Y-axis auto-scale. The axis range is computed only from values within the time window. If the time window cuts off high or low outliers from the wider experiment, the visible scale changes and direct comparison across channels becomes harder.

JSON format dependence. Parsing assumes specific keys ("frame", "mean_luminosity", "channel", "decision"). If PE_Pipeline updates its log format, setpoint_regions_from_log may silently return empty — and the figure will be sparse without an obvious error.

Initial calibration region is suppressed. The first setpoint region is intentionally hidden from the legend (it's pre-experiment stabilization). Don't assume the absence of an early colored band means the system started with no setpoint — there is one, just not displayed.

Frame drops in the log. If logging skipped frames (rare but possible), the line plot has gaps interpreted as straight-line jumps. The controller may have been doing something during those frames that's invisible here.

This is not the cell-level signal. The mean luminosity here is the controller's view of the field — what it used to make decisions. Per-cell dynamics in time_traces may differ, especially for outlier cells that don't follow the population mean.
